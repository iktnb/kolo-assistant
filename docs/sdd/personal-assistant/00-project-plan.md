## Порядок реалізації

1. Узгодити зовнішній контракт і спосіб атомарного збереження до написання інтерфейсу.
2. Реалізувати моделі/валідацію й перевірити календар на зафіксованих датах.
3. Додати сховище з ізольованими тестами перезапуску, пошкодження та збою запису.
4. Додати командний CRUD і пошук для контактів та нотаток; перевірити цілісний шлях через subprocess.
5. Побудувати інтерактивний режим поверх тих самих операцій, спільні рендерери й форми.
6. Додати вбудовану ізольовану демонстрацію, завершити довідку й візуальну перевірку.
7. Пройти незалежні огляди, виправлення, документацію та фактичний запуск.

Функції не дублюють бізнес-правила між командами й меню. Залежності мають бути помірними: Rich для відображення, один придатний CLI-підхід; додаткові бібліотеки — лише за конкретної потреби. Сервісна інфраструктура не потрібна.

## Візуальний напрям

- Образ: спокійний особистий органайзер. Назва «Коло» в короткому заголовку; нижче — компактні лічильники й один очевидний перелік дій. Без декоративних екранів, великих ASCII-заставок і зайвих пауз.
- Невелика семантична палітра: один акцент для навігації, нейтральний для другорядного тексту, окремі успіх/помилка. Кожен стан має текстовий підпис; значки дозволені лише разом із словами. Спільні рендерери забезпечують однаковий стиль.
- Списки контактів: ID, ім'я, основний телефон, email за наявного місця; повна адреса, всі телефони й дата — у деталях. Списки нотаток: ID, заголовок, теги й короткий уривок. Кількість записів і спосіб відкрити деталі видимі.
- На 60 колонках таблиця переходить до компактних стовпців/карток; на 80 — стандартний вигляд; на 120 — більше контексту без надмірного розтягування. Довгі значення переносяться або скорочуються в списку й повністю доступні в деталях.
- Порожній розділ запрошує додати перший запис. Порожній результат пошуку показує сам запит і пропонує змінити його. Помилка поля пояснює очікуваний формат; збереження та скасування мають явний зворотний зв'язок.
- Форми позначають обов'язкові поля, формат дат і телефонів, поточне значення під час редагування, спосіб залишити/очистити поле та скасувати дію. Для нотаток доступне введення тексту з переносами рядків. Рішення щодо завершення багаторядкового вводу архітектор фіксує в довідці.
- Клавіатура достатня для всіх дій; командний режим працює без TTY. Користувацькі значення передаються у Rich як буквальний текст, керувальні символи безпечно відображаються.

## Перевірки та відповідальність за доказ

| Перевірка | Обсяг і спосіб |
|---|---|
| Моделі й негативні сценарії | Межі полів, нормалізація телефонів, email, дублікати, незмінні ID, недопустиме редагування без часткової зміни |
| Календар | Фіксований clock/date; N=0/366, сьогодні, останній включений день, наступний виключений, перехід року, 29 лютого у високосному й звичайному році |
| Сховище | Тимчасовий data-dir; новий процес після запису; імітація невдалого запису; пошкоджені/невідомої версії дані з порівнянням вмісту до/після |
| CLI | Subprocess без TTY: довідка, створення, пошук, edit, видалення, missing ID, коди/потоки, відсутність ANSI при перенаправленні |
| Інтерактивний режим | Реальний або автоматизований PTY: навігація, повторний ввід помилкового поля, збереження введених значень, Ctrl+C, EOF, негативне підтвердження |
| Візуальний огляд | PTY шириною 60/80/120; українські й довгі значення, порожні стани, помилки; `[bold]` та ESC у даних не інтерпретуються |
| Demo та запуск | Відбиток стандартного data-dir до/після `demo`; вигадані дані; чистий запуск за README через абсолютний шлях до uv |
| Повна якість | Усі тести проєкту, форматування/статичні перевірки за обраною конфігурацією, застосовні перевірки безпеки; відсутні перевірки позначено NOT RUN із причиною |

Тести не торкаються особистих контактів/нотаток і не читають `.env`. Відсутній тестовий baseline не називається успішним baseline. Звіти мають посилатися на конкретні файли, команди, assertions і результати; не достатньо лише твердження «перевірено».
